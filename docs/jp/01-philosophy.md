# 01. 基本思想

## なぜ「メッセージ指向」と呼ぶのか

このプロジェクトでは、現代一般に使われる「オブジェクト指向」という語との混同を避けるため、本書で扱うモデルを「メッセージ指向」と呼びます。

中心にあるのはクラス、継承、getter / setter ではありません。

中心にあるのは、状態を持つ独立した主体が、互いの内部へ直接入り込まず、メッセージによって協調することです。

## 基本モデル

各オブジェクトは状態機械として考えます。

    Object = State + Message handling + State transition

オブジェクトは受け取ったメッセージと現在の状態をもとに、自分自身で処理と状態遷移を決めます。

    (Current State, Incoming Message)
        ->
    (Next State, Outgoing Messages)

この式は概念モデルです。実装を純粋関数に限定するという意味ではありません。

## 境界

本設計で最も重要な境界は次です。

    オブジェクト間 = Message
    オブジェクト内部 = Function Call

他のオブジェクトに処理を依頼するために、そのオブジェクトの内部関数を直接呼び出してはいけません。

オブジェクト内部では通常の関数呼び出しを使用できます。外部から受け取ったメッセージを、内部の関数呼び出しへ変換するのが Message Receptor の役目です。

## 継承について

継承はメッセージ指向の成立条件ではありません。

同じメッセージを異なるオブジェクトがそれぞれ解釈できれば、多態的な振る舞いは共通の親クラスを必要としません。

継承を使うこと自体を禁止しませんが、継承を使っていることをメッセージ指向である根拠にはしません。親クラスの内部状態や実装への依存がオブジェクトの独立性を壊していないかは別に検討します。

## 目的

システムが巨大化しても、各主体の責務と状態の所有者を局所化し、領域を越える依存をメッセージとして明示できる構造を目指します。
